# 08 - 选片简述贯通

**What to build:** 用户说"选三张有景有人、表情活泼的照片发朋友圈"，他描述的**题材偏好**与**叙事要求**真正影响选出哪几张、以及它们的顺序。

这是整个增量的头条用户故事。前面几票让机器有能力按描述选片，本票把用户的话接进去。

**选片简述是一个自由文本字段，不拆结构化字段**（PRD 决策二）：agent 把用户意图里跟"选哪几张、怎么排"有关的部分提炼成一段话，经 headless 参数传进 core。不拆成用途/题材/叙事三个字段，因为 core 拿到之后唯一要做的就是把它们拼回一段提示词，中间那层结构没有消费者；而且将来给用户意图新增成分（比如审美偏好）不用动跨进程接口。

**不直接透传意图原文**：原文里混着去重、服务商选择、寒暄等跟选择无关的内容，透传等于让选择提示词被噪声污染，也等于把"理解用户"漏进了 core。提炼是 agent 的活。

**引导语必须同票扩写**（PRD 决策三）：提示不改，用户永远只说"选3张发朋友圈"，抽出来的选片简述就是空的，整条通路是死的。票 02 已把示例收敛成单一常量，本票只需改那一处。

**Blocked by:** 02（引导语收成单一常量）、06（模型选择与排序接进 curate）

**Status:** done（2026-08-02，含 Telegram 端到端真机验收）

- [x] 用户说"选三张有景有人、表情活泼的照片发朋友圈"时，抽出的选片简述包含题材偏好
- [x] 同一句话里的张数与用途解析不受影响（数量为 3、用途为朋友圈）
- [x] 用户只说"选3张发朋友圈"时，选片简述为空或仅含用途，流程不报错
- [x] 用户表达叙事要求（如"按时间顺序"）时，该要求进入选片简述并影响最终顺序
- [x] 选片简述经 headless 参数传抵 core，并进入模型的选择提示词
- [x] 意图原文里与选择无关的成分（去重、服务商、寒暄）不进入选片简述
- [x] 引导语示例已扩写，且全部五处来自同一常量
- [x] 真机验证：换一句题材要求，选出的照片随之改变

## 落地记录

**core 侧不动 `curate_impl` 与 `SelectFn`，简述捕获进 production 的选择
lambda。** 沿的是同一个文件里 `evaluate_and_store` 那条 lambda 捕获
provider/local_config 的先例：简述对 curate 的编排逻辑完全不透明（不读、不
据它分支），而 `SelectFn` 的两个参数是 curate 真正决定的东西（给谁看、选几
张）。代价是"cli 参数 -> core -> 提示词"这一段没有自动化用例（cli 层没有命
令级 JSON 测试的先例，票 06 落地记录已记过同一个缺口），补法见下面的假
Ollama 冒烟。

**`selection_brief` 排在 `curate()` 所有回调之后**（code review 抓到的一
条）：`nullptr` 能隐式转成 `const char*` 再进 `std::string`，参数若挨着语义
相邻的 `local_config`，一个想把 `on_progress` 置空的位置参数调用就会静默构
造出 UB 而不是编译错误。位置难看好过一个不报错的雷。

**`--brief` 不看 `--ai`。** 关 AI 时 core 自己忽略它（那条路径是确定性的，
没有能读这段话的东西），agent 侧也就不再判一次 - 判了等于把"谁消费这个字
段"的知识复制到第二个地方。

**去重追问那一处也接了简述，超出票面但不接就是死路。** 票 02 把示例收敛成
带 `verb` 参数的函数，五处共用；本票一扩写，去重追问那句"要筛选就告诉我留
几张、想发去哪，比如'留三张有景有人、表情活泼的照片发朋友圈'"也跟着示范了
题材偏好。用户照着说而 `DedupFollowupReply` 接不住，就是 PRD 决策三点名的
那种"引导语是死的"。于是给它加了 `selection_brief`，**None 与空串刻意不
同**：None = 这次没说，`_curate_narrow_pending` 里整个不放这个 key，
`rerun_stage` 的 `params.update()` 语义会保留组装意图时抽出来的那一份；空串
会把它冲掉。

**端到端冒烟（票 06 记的那个 cli 缺口的替代验证）**：`XDG_CONFIG_HOME` 指到
临时目录（config 与 db 都认这个变量），`ollama_base_url` 指到一个假
Ollama，跑 `pzt curate --count 2 --ai --provider local --brief "..."`。四个
请求：三次带图的评估 + 一次纯文本选择，简述**逐字出现在第四个请求体的选择
提示词里**（"The user asked for this, in their own words ... 要有景有人、表
情活泼的，发朋友圈"），约束解码的 `format` 与 `temperature=0` 不受影响；不
带 `--brief` 时那一整段不出现。

**真实本地模型（gemma4:e2b）跑出来的抽取质量**，验收标准一/二/三/六靠这个而
不是靠注入假 http_post 的用例（那些验的是接线）：

| 意图 | count / tag | selection_brief |
|---|---|---|
| 选三张有景有人、表情活泼的照片发朋友圈 | 3 / 朋友圈 | `发朋友圈用，要有景有人、表情活泼的照片` |
| 你好呀～先去重，然后用 gemini 挑5张有小孩的，按拍摄时间顺序排 | 5 / 精选 | `有小孩的，按拍摄时间顺序排` |
| 选3张发朋友圈 | 3 / 朋友圈 | `发朋友圈用` |
| 帮我筛一下，留9张 | 9 / 精选 | `` |

第二行是验收标准六：寒暄、去重、`用 gemini` 三样噪声都没进简述，
provider=gemini 与 count=5 各自进了自己的字段。

**提示词的第一版会凭空编题材偏好，是跑真实模型才发现的。** 初版拿引导语那
句"选三张有景有人、表情活泼的照片发朋友圈"当唯一的示例，结果用户只说"选3张
发朋友圈"时模型照着例子补出 `发朋友圈用，要有景有人` - 一段用户从没说过的
偏好，会真的改变选出哪几张。改成四个成对示例（其中两个的简述为空/仅含用
途）并明写"never invent a preference the user did not state"之后复测，同一
句话给的是 `发朋友圈用`。**注入假 http_post 的用例永远抓不到这一类，它们喂
的是罐头答案。**

**顺带修掉两处票 08 之前就有的缺陷**（都是跑真实模型撞出来的，各自独立成一
次提交）：

1. `apply_tag` 显式为 null 时整次方案组装失败。`decision.get("apply_tag",
   "精选")` 只在 key 缺席时兜底，模型回 null 给的是 `None`，被
   `validate_plan` 拒掉。真机上"先去重，然后挑5张有小孩的"这种没提目的地的
   说法就会走到（同一句话跑两次，一次 null 一次正常）。改动前的代码复现过，
   不是本票引入的。
2. agent 自己那次 LLM 调用的超时写死 60 秒，跟 core 上一条提交刚从 60 提到
   180 的是同一个数字、同一个坑。本票把 compose 的提示词加长之后实测复现：
   短意图 40 秒过，带寒暄和去重的长意图稳定卡满 60 秒报 `timed out`，用户看
   到的是意图没被解析。取跟 core 同一个值 180，改完同一句话 53.9 秒跑通。

**没做的一件事：选片确认阶段的调整不认简述。** 用户在选片确认阶段说"换成
有人的那几张"改不了 `selection_brief`，只能改 count/tag/exclude。这不在票面
上，也没有验收标准要求。**已单独成票 11**（2026-08-02）。

## 真机验收（2026-08-02）

最后一条验收标准由用户在真机上跑通并确认。同一天的真机反馈另外打出三个缺
陷，都已随后修掉（`a7a1b5d`..`a841aad`）：

1. **简述从头到尾不可见**。抽取和传送其实一直是好的，但确认文案只说
   count/tag/AI 三件事，用户没有任何地方能核对自己那句题材要求被认成了什
   么，因而判定"brief 没被识别"。方案确认与状态查询两处现在都原样显示简述。
2. **只有一个笼统形容词时，简述会把它整个吃掉**。"选一张比较活泼的照片发
   Facebook" 抽出来只剩"发 Facebook 用"。根因是本票写进提示词的
   `"选3张发朋友圈" -> "发朋友圈用"` 那条例子跟它结构太像，模型照着只留了
   目的地 - 而这会实打实改变选出哪几张。
3. **顺带打出一个不属于本票的 bug**：修第 2 条加的规则挤掉了 `count` 的注
   意力，"选一张"从 count=1 塌成 null，而 null 会走下游默认的 9 张。A/B
   干净（旧提示词两次都给 1，新提示词两次都给 null），根因是 count 规则的
   中文数字例子只举了"三/两"没有"一"，原先是踩线过的。

第 2、3 条都是**只有真模型能发现**的问题：注入假 `http_post` 的自动化测试
验的是接线，罐头响应永远绿。两条已进 `tests/eval_offline/run_eval.py`。
