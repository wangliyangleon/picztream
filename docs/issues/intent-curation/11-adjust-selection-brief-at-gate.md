# 11 - 选片确认阶段能改题材要求

**What to build:** 让用户在看到选片结果之后，能用一句话改**题材要求**并重选，
而不是只能改数量、标签、或点名换掉第几张。

今天在选片确认阶段（`AWAITING_GATE`，Style 闸门阶段一），用户打的字走
`compose/adjustment_parser.py` 的 `classify_gate_reply`，它认得的 adjust
action 只有三个：

| action | 例句 | 落到 |
|---|---|---|
| `set_count` | "留5张" | `PlanDelta(Curate, {"count": 5})` |
| `set_apply_tag` | "标签换成 朋友圈投稿" | `PlanDelta(Curate, {"apply_tag": ...})` |
| `swap_out` | "换掉第3张" | 把那张加进 `exclude` |

**没有一条能改 `selection_brief`。** 用户说"要活泼一点的"、"换成有人的那几
张"、"别都是风景"，落不到任何 action 上 - 要么被判成 `unknown_action`（用户
收到一句听不懂），要么被硬塞进上面三个里的某一个（更糟：静默做了别的事）。

这在票 08 落地时就被点名为"没做的一件事"，当时不在票面上。真机跑过之后它变
得更刺眼：票 08 刚刚把简述做成了**用户唯一能表达题材偏好的通道**，而这个通
道在"看到结果之后"这个最该用它的时刻是断的。用户此刻手里有的信息最多 - 他刚
看完选出来的照片，最知道哪里不对。

**Blocked by:** 08（选片简述贯通，已 done）

**Status:** 已实现（2026-08-02），**未收口** - 第一条验收在 deferred 流程上被票
12 挡住，"重选只花一次文本调用"待真机验。票 12 落地后重验这两条才能标 done。

## 拍板（2026-08-02）

**决策一：新简述到来时，已累积的 `exclude` 保留。**

理由是 `exclude` 的语义是**对具体某一张照片的否定**，跟用哪条标准挑无关；换了
题材要求不会让那张照片重新变得可接受。三条支撑：

1. **与现有行为一致。** `exclude` 今天已经跨 `set_count`/`set_apply_tag` 保留
   （`adjustment_parser.py:162-167` 每次都从 `curate_spec.params` 读旧值再追
   加）。若简述变更清空它，简述就成了三个 adjust action 里唯一会擦掉别人状态
   的特例，用户无从预测。
2. **组合句没有顺序歧义。** 验收标准要求"把第 3 张换掉，要活泼点的"两件事都
   生效。清空的话，同一句话里产生的 `exclude` 会被同一句话里的 brief 变更擦
   掉，结果取决于两个字段的应用先后 - 这不是实现细节，是语义上的不确定。
3. **失败形状更轻。** 保留的坏处是被否掉的照片再也回不来（今天没有反向操作）；
   清空的坏处是用户明确说过"换掉第 3 张"的照片重新出现，读起来像系统忘了指令。
   后者是可见的失信，前者是能力缺口。

**已知代价（记档，不在本票范围）：** 今天没有任何路径能把一张照片从 `exclude`
里放回来。清空方案本可以当一条隐式撤销路径用，选了保留就等于放弃它。若真机上
"误否掉一张想要的"变成实际痛点，那是一张新票（显式的撤销 action），不是在本票
里顺手加。

**决策二：新简述整体替换旧简述，任一时刻只有一条生效。**
（**已于 2026-08-03 修订为"让模型决定"，见本节末尾的"决策二修订"。下面这段
保留原文，记录当初的推理。**）

累加会让简述随轮数变长、权重被稀释，且前后矛盾时（先"多要风景"后"别都是风景"）
拼出来的提示词自相矛盾，模型行为无定义。让 meta 模型合并表达力最强，但要在
`_GATE_SCHEMA_INSTRUCTION` 上加合并规则 - 正是票 08 真机反馈点名的风险（加规
则会挤掉别的字段），且合并结果不确定、测试只能做模糊匹配。

替换的安全网是本票已有的验收项**"回显的确认文案带上新简述"**：用户每轮都看得
见此刻生效的是哪一句，想同时要两个条件就重说一句合并的。没有这条回显，替换会
变成静默丢失；有了它，替换是自纠正的。**这两条是绑定的，实现时不能只做替换、
把回显往后放。**

### 决策二修订（2026-08-03，真机之后）

**改为：不规定合并还是替换，让模型自己决定。** 原拍板选"替换"、否掉了第三个选
项"让 meta 模型合并"，理由是合并结果不确定、简述会随轮数变长、前后矛盾时提示词
会自相矛盾。真机跑下来这几条担心没有兑现，而合并出来的结果是可用的：

```
旧简述 '发朋友圈用，要有景有人的'  +  用户说 '要整体气氛活泼的照片吧'
模型交回 '整体气氛活泼的，要有景有人的'
```

它丢掉了已经由 `apply_tag` 承载的"发朋友圈用"，留下了两条真正的题材要求。用户判
断这个行为可以接受，因此不再强制替换。

**这条修订的实际含义是"不写规则"，不是"改成累加"。** 提示词里对
`selection_brief` 没有任何合并/替换的指示，模型按上下文自己判断。曾经试过写死
`REPLACE entirely, never merge`：能纠正行为，但 `_CONFIRMATION_SCHEMA_INSTRUCTION`
涨到 2395 字符后本地模型开始把整个返回结构改成嵌套的 `{"confirmed": {...}}`（同
票 13 落地记录里那次），代价不值。

**两条路径因此行为不同，这是结构性的，不是漏改：**

| 路径 | 提示词里有没有旧简述 | 实际行为 |
|---|---|---|
| 方案确认（`PLANNED` / `refine_plan_confirmation`） | 有（`_plan_summary` 带进去） | 模型可以合并，实测会合并 |
| 选片确认（`AWAITING_GATE` / `classify_gate_reply`） | **没有**（那个提示词只吃用户这一句） | 模型无从合并，结果是替换 |

要让两条一致，得往 gate 那条的提示词里塞当前简述 - 那是另一件事，且同样要过本地
模型的稳定性这一关，没有真机诉求之前不做。

## 开工前仍需回答（Eng Design 级，不阻塞拍板）→ 已答，见落地记录

1. **组合句在 gate schema 上怎么表达。** 今天 `classify_gate_reply` 返回单个
   action，`_decision_to_delta` 一次只产一个字段的 `PlanDelta`。要让"换掉第 3
   张 + 改简述"两件事都生效，是新增一个 `set_selection_brief` action 并允许一
   次返回多个 action，还是让现有 action 各带一个可选的 brief 字段？前者动
   `GateReply` 的形状，后者会把简述抽取重复进三个 action 的说明里。
2. **决策二的"替换"在没提简述的轮次里不能误伤。** 用户只说"留 5 张"时，delta
   里不该出现 `selection_brief` 键 - 否则按替换语义会把旧简述清成空。区分"没
   提到"与"明确要求去掉题材限制"需要在 schema 上留出表达。

## 三件开工前该知道的事

**一、重选很便宜，但便宜的原因要说准。** 改简述之后走 `rerun_stage(run,
"Curate", params)`，整个 Curate stage 重跑：分簇（本地、确定性）→ 预选集
（本地、确定性、同一批照片同一个结果）→ 评估（**全部命中缓存**，票 05 的判
据是"有评估记录就跳过"）→ 选择（一次纯文本调用，吃新简述）。所以代价是**一
次文本调用**，不是重跑一遍分钟级的评估。这条性质值得在用户话术里体现（"稍等
几秒"而不是"要几分钟"）。

**二、能改的只是"在预选集里怎么选"，改不了预选集本身。** 预选集是确定性多样
性预筛从候选集裁出来的，只看 `captured_at`，跟简述无关（PRD 决策十）。所以
"换成有人的那几张"如果预选集里压根没有几张有人的，重选也变不出来。这是
PRD 风险一的同一条边界，不是本票的缺陷，但**用户话术不能暗示能力比实际大**
- 重选之后如果结果几乎没变，得能说清为什么。

**三、跟 `swap_out` 的语义关系已拍板：`exclude` 保留、简述替换。** 见上面
"拍板"一节。要注意 `exclude` 并不进模型 - 它是**结果上的后置过滤**
（`curate.py:47` 向 core 多要 `count + len(exclude)` 张，`:68` 拿回来再滤掉、
截断到 `count`）。所以重选时模型完全不知道有哪几张被否过，可能仍把它选进来，
再被过滤掉。这不影响正确性，但意味着 `exclude` 越多、多要的张数越多，簇不够时
最终交付可能不足 `count` 张。

## 落地记录（2026-08-02）

两个 Eng Design 问题的答案：

**一、组合句：给现有三个 adjust shape 各挂一个可选 `selection_brief` 字段，另
加一个只改题材要求的 `set_selection_brief` action。** 没走"一次返回多个 action"
那条 - `GateReply` 的形状不用动，`parse_adjustment` 也不受影响。票里担心的"简述
抽取会重复进三个 action 的说明里"靠写法避开了：可选字段的说明在
`_GATE_SCHEMA_INSTRUCTION` 末尾统一写一次，不逐个 action 重复。新 action 只进
`_GATE_ADJUST_ACTIONS`，故意不并进 `_ADJUST_ACTIONS`（那个元组还管着
`parse_adjustment`，而它的提示词从没提过这个 action）。

**二、None/`""` 的区分沿用票 08 立的约定。** 缺席 / `null` / 非字符串都归成"这
次没提"，key 整个不进 `PlanDelta`（`params.update()` 语义下，不放 key 才是"不动
旧值"）；空串是"明确要求去掉题材限制"的一次有意覆盖，必须放进去。这套约定票 08
已经在 `DedupFollowupReply.selection_brief` 上写过一遍，两处不该各有一套。

**决策一是自动成立的，不需要专门写代码：** 简述只经 `params.update()` 进
Curate，`_resolve_swap_out` 的 `exclude` 合并逻辑一个字没改。组合句里两件事进同
一个 delta、一次 update，谁先谁后不影响结果。

**回显做了两处而不是一处（超出验收标准字面）：** 验收只要求"改完之后回显的确认
文案带上新简述"，实际做的是：闸门消息（`_render_selection_confirm_gate`）**每次**
都带（不只改完那次，第一次进闸门时若已有简述也带），且 `view.describe()` 的
`AWAITING_GATE` 分支也带。理由是票 08 已经在 `view.py` 的 PLANNED 分支上写明
"状态查询是用户核对选片简述的第二个入口，两处说法不一致会让用户以为方案变过" -
那条理由对这个闸门同样成立，而当时只覆盖了 PLANNED。两处共用
`view.describe_selection_headline()` 一个函数，措辞不会分叉；闸门消息是
`按你说的「…」选好了 N 张`，状态查询多一个既有的前缀，是`已经按你说的「…」选好
了 N 张`。两个入口读的源不同（闸门读活的 `run.plan`，`describe()` 读
`view.plan_summary` 快照），一致性靠 `_on_gate_reached` 每次重新
`load` + `view_from_run` 保证，有测试钉住。

**落地时发现一个既有缺陷，单独成票 12（`12-rerun-stage-leaves-its-gate-armed.md`）。**
`rerun_stage` 答完的闸门不解除 `spec.gate`，导致"只说去重没给数量"那条流程里，选
片确认闸门上的**任何**一次调整都会把"要不要再筛选一下"再问一遍、Curate 不重跑。
它对现有三个 action 一视同仁、早于本票存在，修法要动 `orchestrator/driver.py`
（本票范围是 `agent/compose` + `agent/session`）且与票 10 的 rewind、AG-01 的
Style 重问共用 gate 生命周期，因此没在本票里顺手改，只用一个测试钉住了现状。
**本票下面前两条验收在那条 deferred 流程上要等票 12 才成立**，在"一开始就给了
数量"的主流程上已成立（那条路径的 `curate.gate` 早被 `_apply_confirmed_plan_params`
置成 `off`）。

## 验收标准

- [ ] 选片确认阶段说"要活泼一点的"/"换成有人的那几张"/"别都是风景"，能改到
      `selection_brief` 并重选
      - **主流程（一开始就给了数量）成立**；**deferred 流程（只说去重没给数量）
        不成立**，被票 12 那个既有缺陷挡住：调整会把"要不要再筛选一下"再问一
        遍、Curate 不重跑。**票 12 落地前这条不算完成**
- [ ] 重选只花一次文本调用，不重跑评估（用已评估过的项目验，看进度里没有评估段）
      - 依赖 core 的评估缓存（票 05"有评估记录就跳过"），本票无代码改动，**待真机验**
- [x] 改完之后回显的确认文案带上新简述（票 08 真机反馈定的规矩：简述必须可见）
- [x] 一句话里同时给了题材要求和别的调整（数量/标签/换掉第几张）时，两件事都生效

## 真模型结果（本地 Ollama，2026-08-02）

10 条 gate 用例，9 条如预期。最关键的两条组合句（新可选字段最容易在这里把原有
字段挤掉）是好的：`把第3张换掉，要活泼点的` → `{exclude:[c.jpg],
selection_brief:'要活泼点'}`，`留5张，要有人的` → `{count:5,
selection_brief:'要有人的'}`。没提题材要求的两条也干净，没有凭空造简述。

**唯一没到位的是空串清除。** `不用管题材了，随便选` 第一轮被判成 `approve`（危
险：会跳过重选直接去交付），把这条规则从末尾的 "Additionally" 段挪进
`set_selection_brief` 自己的 shape 说明、并写明"这是要求重选、不是同意"之后，
第二轮变成 `adjust` + `selection_brief:'随便选'`。**仍不是空串**，但失败模式已
经从有害降成无害 - "随便选"作为题材要求喂给 core 约等于无约束。空串那条分支代
码和单测都在，只是本地模型不往那儿走。要真的收干净，得等下一次 prompt 迭代或换
个更强的 meta provider，不值得为它把已经验证好的 9 条重新洗一遍。
