# 11 - 选片确认阶段能改题材要求

**What to build:** 让用户在看到选片结果之后，能用一句话改**题材要求**并重选，
而不是只能改数量、标签、或点名换掉第几张。

今天在选片确认阶段（`AWAITING_GATE`，Style 闸门阶段一），用户打的字走
`compose/adjustment_parser.py` 的 `classify_gate_reply`，它认得的 adjust
action 只有三个：

| action | 例句 | 落到 |
|---|---|---|
| `set_count` | "留5张" | `PlanDelta(Curate, {"count": 5})` |
| `set_apply_tag` | "标签换成 朋友圈投稿" | `PlanDelta(Curate, {"apply_tag": ...})` |
| `swap_out` | "换掉第3张" | 把那张加进 `exclude` |

**没有一条能改 `selection_brief`。** 用户说"要活泼一点的"、"换成有人的那几
张"、"别都是风景"，落不到任何 action 上 - 要么被判成 `unknown_action`（用户
收到一句听不懂），要么被硬塞进上面三个里的某一个（更糟：静默做了别的事）。

这在票 08 落地时就被点名为"没做的一件事"，当时不在票面上。真机跑过之后它变
得更刺眼：票 08 刚刚把简述做成了**用户唯一能表达题材偏好的通道**，而这个通
道在"看到结果之后"这个最该用它的时刻是断的。用户此刻手里有的信息最多 - 他刚
看完选出来的照片，最知道哪里不对。

**Blocked by:** 08（选片简述贯通，已 done）

**Status:** ready-for-agent（拍板于 2026-08-02，见下）

## 拍板（2026-08-02）

**决策一：新简述到来时，已累积的 `exclude` 保留。**

理由是 `exclude` 的语义是**对具体某一张照片的否定**，跟用哪条标准挑无关；换了
题材要求不会让那张照片重新变得可接受。三条支撑：

1. **与现有行为一致。** `exclude` 今天已经跨 `set_count`/`set_apply_tag` 保留
   （`adjustment_parser.py:162-167` 每次都从 `curate_spec.params` 读旧值再追
   加）。若简述变更清空它，简述就成了三个 adjust action 里唯一会擦掉别人状态
   的特例，用户无从预测。
2. **组合句没有顺序歧义。** 验收标准要求"把第 3 张换掉，要活泼点的"两件事都
   生效。清空的话，同一句话里产生的 `exclude` 会被同一句话里的 brief 变更擦
   掉，结果取决于两个字段的应用先后 - 这不是实现细节，是语义上的不确定。
3. **失败形状更轻。** 保留的坏处是被否掉的照片再也回不来（今天没有反向操作）；
   清空的坏处是用户明确说过"换掉第 3 张"的照片重新出现，读起来像系统忘了指令。
   后者是可见的失信，前者是能力缺口。

**已知代价（记档，不在本票范围）：** 今天没有任何路径能把一张照片从 `exclude`
里放回来。清空方案本可以当一条隐式撤销路径用，选了保留就等于放弃它。若真机上
"误否掉一张想要的"变成实际痛点，那是一张新票（显式的撤销 action），不是在本票
里顺手加。

**决策二：新简述整体替换旧简述，任一时刻只有一条生效。**

累加会让简述随轮数变长、权重被稀释，且前后矛盾时（先"多要风景"后"别都是风景"）
拼出来的提示词自相矛盾，模型行为无定义。让 meta 模型合并表达力最强，但要在
`_GATE_SCHEMA_INSTRUCTION` 上加合并规则 - 正是票 08 真机反馈点名的风险（加规
则会挤掉别的字段），且合并结果不确定、测试只能做模糊匹配。

替换的安全网是本票已有的验收项**"回显的确认文案带上新简述"**：用户每轮都看得
见此刻生效的是哪一句，想同时要两个条件就重说一句合并的。没有这条回显，替换会
变成静默丢失；有了它，替换是自纠正的。**这两条是绑定的，实现时不能只做替换、
把回显往后放。**

## 开工前仍需回答（Eng Design 级，不阻塞拍板）

1. **组合句在 gate schema 上怎么表达。** 今天 `classify_gate_reply` 返回单个
   action，`_decision_to_delta` 一次只产一个字段的 `PlanDelta`。要让"换掉第 3
   张 + 改简述"两件事都生效，是新增一个 `set_selection_brief` action 并允许一
   次返回多个 action，还是让现有 action 各带一个可选的 brief 字段？前者动
   `GateReply` 的形状，后者会把简述抽取重复进三个 action 的说明里。
2. **决策二的"替换"在没提简述的轮次里不能误伤。** 用户只说"留 5 张"时，delta
   里不该出现 `selection_brief` 键 - 否则按替换语义会把旧简述清成空。区分"没
   提到"与"明确要求去掉题材限制"需要在 schema 上留出表达。

## 三件开工前该知道的事

**一、重选很便宜，但便宜的原因要说准。** 改简述之后走 `rerun_stage(run,
"Curate", params)`，整个 Curate stage 重跑：分簇（本地、确定性）→ 预选集
（本地、确定性、同一批照片同一个结果）→ 评估（**全部命中缓存**，票 05 的判
据是"有评估记录就跳过"）→ 选择（一次纯文本调用，吃新简述）。所以代价是**一
次文本调用**，不是重跑一遍分钟级的评估。这条性质值得在用户话术里体现（"稍等
几秒"而不是"要几分钟"）。

**二、能改的只是"在预选集里怎么选"，改不了预选集本身。** 预选集是确定性多样
性预筛从候选集裁出来的，只看 `captured_at`，跟简述无关（PRD 决策十）。所以
"换成有人的那几张"如果预选集里压根没有几张有人的，重选也变不出来。这是
PRD 风险一的同一条边界，不是本票的缺陷，但**用户话术不能暗示能力比实际大**
- 重选之后如果结果几乎没变，得能说清为什么。

**三、跟 `swap_out` 的语义关系已拍板：`exclude` 保留、简述替换。** 见上面
"拍板"一节。要注意 `exclude` 并不进模型 - 它是**结果上的后置过滤**
（`curate.py:47` 向 core 多要 `count + len(exclude)` 张，`:68` 拿回来再滤掉、
截断到 `count`）。所以重选时模型完全不知道有哪几张被否过，可能仍把它选进来，
再被过滤掉。这不影响正确性，但意味着 `exclude` 越多、多要的张数越多，簇不够时
最终交付可能不足 `count` 张。

## 验收标准

- [ ] 选片确认阶段说"要活泼一点的"/"换成有人的那几张"/"别都是风景"，能改到
      `selection_brief` 并重选
- [ ] 重选只花一次文本调用，不重跑评估（用已评估过的项目验，看进度里没有评估段）
- [ ] 改完之后回显的确认文案带上新简述（票 08 真机反馈定的规矩：简述必须可见）
- [ ] 一句话里同时给了题材要求和别的调整（数量/标签/换掉第几张）时，两件事都生效
- [ ] 简述变更时已累积的 `exclude` **原样保留**（决策一），有测试钉住；组合句
      里同时产生的 `exclude` 与新简述互不擦除，与两者出现的先后无关
- [ ] 新简述**替换**旧简述而非累加（决策二），有测试钉住
- [ ] 没提到题材要求的轮次（如"留5张"）**不**清空已有简述
- [ ] 原有三个 adjust action 的行为不变
- [ ] 简述抽取的质量用真模型验过，不只是注入假 `http_post`（票 08 真机反馈的
      教训：罐头响应永远绿，`_SCHEMA_INSTRUCTION` 上加规则会挤掉别的字段）
