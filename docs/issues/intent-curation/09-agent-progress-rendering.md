# 09 - agent 侧进度渲染

**What to build:** 在 Telegram 那一侧，用户能看到评估的实时进度（"正在评估照片，已完成 7/18 张"）以及跑完时的**终态消息**，而不是分钟级沉默。

票 05 已经让 core 在评估期间往 stderr 的带外通道吐进度行，本票把它渲染成人话。

**必须新增第四个进度类别**（PRD 决策二十）：agent 侧现有的进度类别维度同时扛着**单位**和**在干什么**两件事。现有三类里虽然已有单位为"张"的一类，但它的活动被"套滤镜"占用，复用会让用户看到"正在套滤镜，已完成 7/18 张"这种明显说错的话。

本票**只加第四类，不拆**这个维度。拆是更大的改动，收益不足以在这一刀里做。这笔债记在 PRD 决策二十里。

**终态消息不可省**（T-8 真机反馈的既有教训）：进度若停在"正在…"上，用户看到的最后一条永远是未完成态，然后下一件事无预警发生。跑完必须有一条明确的完成消息。

## phase 共存的处置（已拍板）

**这一节是本票原本缺的那块，不定下来无法开工。**

票 05 之后，开 AI 的 curate 一次 run 会在同一个 Curate stage 里先后发三个 phase：`cluster` -> `compare` -> `evaluate`（顺序见 `core/curate/curate.cpp`，`cluster_and_choose` 返回之后才裁预选集、才逐张评估）。而 `agent/stages/progress.py` 的 `forwarding()` 明确规定"一个 run 里只转发一个 phase"，开 AI 时选的是 `compare`。**照本票原有措辞直接加第四类，`evaluate` 会被 `forwarding()` 丢掉，第一条验收标准根本达不成。**

那条单 phase 约束的原始理由是分母不同源会让进度看着倒退，这个顾虑在本票里是真的。举两个例子（进度是**同一条消息原地编辑**，且 `done >= total` 那一帧不受 60 秒节流约束，所以下面的跳变必现而不是偶发）：

- 200 张照片、40 个候选簇、要 3 张、M=2：比较 160 次、评估 6 张。用户看到"已完成 160/160 次"之后紧接着变成"已完成 1/6 张"。
- 32 张照片、30 个簇（只有 2 个簇需要比较）、要 10 张、M=2：比较 2 次、评估 20 张。用户看到"已完成 2/2 次"之后变成"已完成 1/20 张"，分子分母同时跳，正是 `forwarding()` 注释里担心的那个形状。

**采用切换转发 + phase 级终态**：`evaluate` 的第一帧到达之前，先把 `compare` 那条收尾成终态（"两两比较跑完了，共 N 次"），评估另起一条消息。

代价是 Curate 期间占两条进度消息，**明确偏离 AG-16.3"进度只占一条"**。可以偏离的理由：那条约定针对的是"每个 stage 再追一条完成消息会把对话刷成流水账"，而这里两条消息数的是不同的东西、单位也不同（次 / 张），挤在一条里必然有一边说错。还有一个附带收益：不这么做的话 `_finalize_stage_progress()` 只在 stage 边界触发，"两两比较跑完了，共 N 次"这句永远发不出去，会被评估的第一帧原地覆盖 - 那等于悄悄改掉了现有比较进度的行为，与本票"现有三类措辞与行为不变"自相矛盾。

**被否掉的两条**：

- *只转发 `evaluate`、放弃比较进度*：比较那一段同样是分钟级，等于用一段新的静默换掉另一段。
- *合并成一个总分母*（如"已完成 12/166 项"）：两段单位不同，T-8 的真机验收已经推翻过"把 phase 压掉、单位不跟着数字走"的做法（见 SPEC §3.2）。

**仍然不做的事**：不拆"单位 + 在干什么"这个维度，立场同上文，债仍记在 PRD 决策二十。

实现要碰的地方（列出来只为省去重新摸索，不规定写法）：`agent/orchestrator/stage.py` 的 `PROGRESS_*` 常量、`agent/session/view.py` 的 `_PROGRESS_PHRASINGS`/`_PROGRESS_DONE_PHRASINGS`、`agent/stages/progress.py` 的 `forwarding()`、`agent/session/consumer.py` 的 `_on_stage_progress`/`_finalize_stage_progress`（换槽 + 收尾的先例已经有一个：`_on_stage_started`）。
