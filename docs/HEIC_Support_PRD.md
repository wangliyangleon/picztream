## 一、问题陈述

`SPEC.md` §1 定下核心用户是**有技术背景的摄影爱好者**，手机摄影是一等场景，格式优先级 **JPEG 与 HEIC = P0**。

但 HEIC 目前**完全不被支持**，而 iPhone 自 iOS 11 起在 A10 及以上机型的**出厂默认拍摄格式就是 HEIC**。后果对核心用户是开箱即坏：

- 他把手机照片导到一个文件夹、跑 `pzt new`，得到的是 `'<path>' 目录下没有找到任何 JPEG/RAW 文件`。
- 这句话在一个塞满照片的目录上是**事实错误**，而且主动排除了"是不是格式不支持"这个正确猜想 - 与 U-3 记录的纯 RAW 目录是同一条错误路径、同一句文案。
- 混合目录（部分 JPEG、部分 HEIC）更隐蔽：项目建得出来，只是**少了一部分照片**，且全程无任何提示。用户不会知道自己在对一个残缺的集合选片。

**取出照片的路径决定他会不会撞上这个问题，而默认值互相矛盾**：Photos.app"导出未修改的原始文件"、AirDrop、USB/图像捕捉给 HEIC；"导出 N 张照片…"与 iCloud.com 网页下载默认转 JPEG；Telegram 的 photo 通道服务端转 JPEG，document 通道（"发原图"）保留 HEIC。**越在意画质、越会主动避开转码路径的用户，越会撞上 HEIC** - 也就是核心用户本人。

## 二、解决方案

`pzt` 把 HEIC 当作与 JPEG **同级的一等输入格式**：建项目时收录、选片时秒切浏览、打标签、去重、选片、套风格、导出，全流程与 JPEG 无差别。用户不需要知道自己的照片是什么格式，也不需要任何开关 - **与 RAW 的 opt-in 模型明确不同**，HEIC 没有 opt-in。

已实测确认这在技术上是廉价的：解码、色彩流水线、EXIF 拍摄时间三条路走的都是格式无关的 ImageIO（`CGImageSourceCreateWithData` / `CopyPropertiesAtIndex`），把 HEIC 原样改名成 `.jpg` 之后导入、读 `captured_at`、套 recipe 导出全部成功。**唯一的闸门是扩展名白名单。**

真正需要设计的只有两处：**导出契约**（导出 `.heic` 忠实但发布目的地未必认，转 `.jpg` 通用但多一次有损重编码）与**同名冲突规则**（同一目录下同名的 HEIC 与 JPEG 该留哪个）。

## 四、实现决策

### 决策一：HEIC 不是 opt-in

与 RAW（`--support-raw`，SPEC §3.4）明确不同，HEIC **无条件扫描**，没有开关。依据是 SPEC §1 的格式优先级：JPEG 与 HEIC 同为 P0。给 P0 格式加开关等于把开箱即坏保留下来。

### 决策二：`kind` 列复用 `'jpeg'`，不新增取值

`images.kind` 保持 `'jpeg' | 'raw'` 两个取值，HEIC 记为 `'jpeg'`。

依据是复核了 `kind` 的**全部**下游消费者：`core/project`、`core/export`、`core/api` 里每一处都只判 `== "raw"`，**没有任何一处对 `'jpeg'` 分支**。整个代码库在这一列上问的其实是"要不要走 LibRaw 重路径"这个二值问题。新增 `'heic'` 取值意味着为零消费者付一次 schema 迁移（T-7 已立起 `PRAGMA user_version` 闸门，加取值就得写迁移并升版本），收益为零。

代价是列名从此名不副实。**偿还方式是把该列的语义在头文件与 schema 注释里重新写清楚**："`raw` = 需要去马赛克、走 LibRaw；`jpeg` = 相机/设备已渲染好、走 ImageIO"，并写明 HEIC 属于后者。不改列名（那才是真迁移）。

### 决策三：`decode` 那组函数按事实改名

`decode_jpeg_file` / `decode_jpeg_bytes` / `encode_jpeg_file` / `encode_jpeg_bytes` / `read_jpeg_capture_time` 在吃 HEIC 之后名字即错。本次**改名为格式中性**的名字，机械改动全部调用点。

依据：这个项目已经吃过多次"名字与事实分叉"的亏（`eval`/`compare` 成为无消费者的孤儿命令、`/dedup` 那道语义已失效却还在吓唬用户的闸门、README 按键表写 `g` 而代码是 `f`）。改名成本只随调用点增长，现在最便宜。

**例外**：`encode_*` 那两个仍然只写 JPEG（导出与预览缓存都产 JPEG），它们的名字是准确的，**不跟着改**。只有"读/解"这一侧名不副实。

### 决策四：扩展名白名单收成一处权威定义

`core` 侧现有两个判定函数（JPEG 与 RAW 各一）散在扫描逻辑里。本次把"哪些扩展名算已渲染图片"收成 `core` 内的**单一定义**，扫描、错误文案、以及将来的任何新消费者都从它取。

`agent/transport/watchfolder.py` 里那份 Python 拷贝**照改**（加两个后缀 + 一个测试）。它无法链接 C++，所以仍是第二份实现，**这一点如实记在 T-16 名下、不假装解决了**；但让它与 `core` 保持同一份语义的成本近乎为零，而不改会制造一处新的同名不同义分叉（`pzt new` 收下 HEIC、`run_watchfolder.py` 静默忽略）。

### 决策五：导出无 recipe 时**保留原格式**，不转码

`core/export` 现有逻辑是"`kind == "raw"` 才改扩展名为 `.jpg`，其余字节拷贝"。HEIC（`kind='jpeg'`）因此原样导出成 `.heic`，**名实相符**。本次**维持这个行为**。

依据有三：其一，SPEC §2.4 的"不碰用户数据"精神 - 用户没要求改变的东西不该被有损重编码；其二，无 recipe 的导出在语义上就是"把原图挑出来给我"，转码违背这个语义；其三，套了 recipe 的导出**本来就产 JPEG**（走解码 → 色彩处理 → 重编码），需要通用格式的用户走那条路即可。

**但必须补一条可发现性**：导出目标是 social media 时 `.heic` 未必被接受。因此导出完成的回执里，当本次导出**包含未套 recipe 的 HEIC** 时，加一句说明（大意："其中 N 张按原格式 `.heic` 导出；需要通用格式可先套一个 recipe 再导"）。这条提示只在真的导出了 HEIC 原文件时出现，不套在每次导出上。

> 这一条推翻了本次立项初期的判断。当时以为导出会产出"内容是 HEIC、后缀是 `.jpg`"的错标文件，那是**实验造出来的假象** - 探针把 HEIC 改名成 `.jpg` 才喂进去，`file_name` 本身就是 `.jpg`。真实 `.heic` 输入不会错标。

### 决策六：同名冲突规则

现有规则是"同目录 + 同文件名主干下，**RAW 挤掉 JPEG**"。加入 HEIC 后的完整优先级定为：

**RAW > HEIC > JPEG**（同一主干只产出一条记录）

依据：优先级按"信息量"排，与现有 RAW 挤掉 JPEG 的依据一致 - HEIC 是设备直出的原始渲染结果，同名 JPEG 通常是它的转码副本（iCloud/Photos 导出、AirDrop 到旧设备都会产生这种一对）。留信息量高的那份。

`--support-raw` 关闭时（默认），RAW 分支整个不进，规则退化成 **HEIC > JPEG**。

### 决策七：错误与提示文案按事实重写

`NoImagesFound` 的文案当前写死"JPEG/RAW"。改为**从决策四那份权威白名单派生**，或至少列全当前支持的格式，使它在任何格式组合下都不说假话。i18n 中英两侧同步。这条同时缓解 U-3 记录的纯 RAW 目录场景（那句话仍然会出现，但至少不再是"没有找到任何 JPEG/RAW 文件"这种自我否定的表述）。

### 决策八：`GetPrimaryImageIndex()` 替代硬编码 0

`core/decode` 当前写死 `CGImageSourceCreateImageAtIndex(src, 0, ...)`，改为先取 `CGImageSourceGetPrimaryImageIndex()`。

**这是健壮性改进，不是阻塞风险。** 实测已确认：辅助数据（深度图 / 增益图）**不进图像列表** - 写入一个带 disparity 辅助数据的 HEIC 再回读，`GetCount()` 仍为 1、primary 仍为 0，辅助数据走 `CopyAuxiliaryDataInfoAtIndex` 带外取；连 ImageIO 写出的双图序列容器 primary 也是 0。真正会让 primary 偏离 0 的是 HEIC 图像序列这类多 item 容器，在 iPhone 静态照片上罕见。改用正确 API 是一行、免费、correct-by-construction，因此照做；但**不需要**为它专门搜集人像/HDR 真机样本，也不该把它列为上线前的验收阻塞项。

> 立项初期我判断"人像模式深度图 / HDR 增益图会让 index 0 不保证是主图"，该判断已被上述实测推翻，此处照实记录。

## 五、测试决策

**什么是好测试**：只测对外可观察的行为 - 扫描收录了哪些文件、记录里的字段值、导出产物的格式与文件名、错误文案的内容。不测私有函数、不断言内部调用顺序。

**Fixture 策略（已实测可行）**：HEIC fixture **程序化生成，零二进制素材**。`CGImageDestinationCreateWithData(out, CFSTR("public.heic"), ...)` 可用（实测 64x48 纯色 488 字节），与 `core/tests/decode_test.cpp` 现有的 `encode_solid_jpeg` / `write_jpeg_fixture` 是同一套写法，直接扩一个 UTI 参数即可。注意 `public.heif` **不可写**，只用 `public.heic`。

**四条缝，全部复用现有缝，不新建**：

| 缝 | 测什么 | 现有先例 |
|---|---|---|
| `core::project` 扫描（主缝） | HEIC 被收录；`kind` 为 `'jpeg'`；同名优先级 RAW > HEIC > JPEG；`--support-raw` 关闭时退化成 HEIC > JPEG；混合目录完整收录；`rescan` 把旧项目里被跳过的 HEIC 补进来；一张都没有时的错误文案 | `core/tests/project_test.cpp`，用 `touch()` 空文件测扫描 - 扫描逻辑只看扩展名，HEIC 沿用空文件即可 |
| `core::decode` 解码 | HEIC 解码出正确尺寸与颜色；HEIC 的 EXIF 拍摄时间读得出；primary index 非 0 时取到的是主图 | `core/tests/decode_test.cpp`，已有程序化 fixture helper |
| `core::export` 导出 | 无 recipe 的 HEIC 原样导出成 `.heic` 且字节一致；套了 recipe 的 HEIC 导出成真 JPEG；混合批次两种行为并存；含未套 recipe 的 HEIC 时回执带那句说明 | `core/tests/export_test.cpp` |
| agent watchfolder | `.heic` 被 `_IMAGE_EXTENSIONS` 接受 | `agent/tests/`，现有 transport 测试 |

**需要真机验收（不进自动化）**：一批真实 iPhone HEIC（含人像模式与 HDR）跑完整流程 - 建项目、`pzt open` 秒切、`/dedup --ai`、套 recipe、导出。理由与本项目对 LLM 相关验收的一贯做法一致：这类验证依赖真实素材与真实模型，不适合写成断言。

## 六、范围外

- **Photos 图库入口**（`pzt new` 认识 `.photoslibrary`）。同一缺口的另一半，但按 T-5 的范围裁剪顺延，已记进 `docs/Task_Pool.md`，**立项前值得单独 grill 一次**。
- **RAW 的 opt-in 现状**（`--support-raw` 不进 usage、纯 RAW 目录建不出项目，即 U-3）。RAW 是 P1，排在本条之后，不在本次一并解决。本次只让错误文案不再说假话。
- **HEIC 图像序列 / Live Photo 的动态部分**。Live Photo 的静止图就是普通单图 HEIC，本次自然覆盖；旁边那个 `.MOV` 不在白名单里、继续被忽略，不做视频支持。
- **HEIC 输出**（把导出产物编码成 HEIC）。`encode_*` 仍只产 JPEG。
- **深度图 / 增益图的利用**（人像虚化、HDR 显示）。本次只保证读到主图，不消费辅助数据。
- **其它未支持格式**（PNG、TIFF、WebP、DNG 以外的厂商 RAW 扩展）。本次只加 HEIC，因为只有它是 P0 设备的出厂默认。

## 七、补充说明

- **size 判断**：不是 XS。白名单本身是 XS，但决策五（导出回执）、决策六（同名优先级）、决策七（文案）、决策三（改名的调用点面）加起来是 **S/M**，且决策五与六是对外行为契约，正是本 PRD 存在的理由。
- **与 T-5 的关系**：SPEC 已拍板 **HEIC 入口不计入"下一周期至少一半 deliverable 落回人工选片路径"那一半** - 它让核心用户的照片进得来，但不让选片这件事变好。排期时不要拿它填那个配额。
- **实测底账**（本 PRD 的事实基础，均在隔离库中完成、未写入真实库）：HEIC 原样改名 `.jpg` 后 `pzt new` 收录 4 张、`captured_at` 读出真实 EXIF 值、套 `Tokyo 1966` 导出产出 3088x2316 的真 JPEG；22 张真实 iPhone/iPad HEIC 探针全部 `cnt=1 / primary=0 / 无辅助数据 / 非 Live Photo`（该样本不覆盖人像与 HDR）；ImageIO 可写 `public.heic`、不可写 `public.heif`；带 disparity 辅助数据的 HEIC 回读 `cnt=1 / primary=0`。
- **下一步**：`/to-tickets` 拆成 tracer-bullet 票，票内声明阻塞边。建议的自然切法是按缝切：白名单 + 权威定义 → 同名优先级 → 文案 → 解码改名与 primary index → 导出契约与回执 → agent 白名单。
